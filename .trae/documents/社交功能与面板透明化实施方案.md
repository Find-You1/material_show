# 社交功能与面板透明化 · 实施方案

## Context

站点（对标 Pexels 的图片素材社区）目前是「浏览 + 个人中心 + 后台」的完成态，用户之间没有任何关系。
本轮要补上社交层，让站点从「图库」变成「社区」：

1. **头像支持上传图片** —— 现在账号设置里只能手填一个图片 URL，不实用。
2. **关注 + 关注流 + 站内通知** —— 用户明确选择「两者都要」：首页要有仿抖音的「推荐 / 关注」切换（只看已关注作者的作品），同时对方发布新作品时要给出站内通知与未读红点。
3. **私信（仿抖音）** —— 一对一会话 + 会话列表 + 聊天气泡 + 未读角标，并且要求 **WebSocket 实时推送**。
4. **屏蔽功能** —— 口径是「任何登录用户都能给任何人发私信，但要有屏蔽、不接收特定人消息的能力」。
5. **上传页与账号设置页的面板透明一点** —— 范围严格限定这两页的两个 `.panel`，其他页面（我的上传、收藏、后台表格）保持白底不动。

技术前提（已核实）：路由一律 `def`（同步 SQLAlchemy + PyMySQL）；
`uvicorn[standard]`（含 websockets）与 `Pillow` 已在 `requirements.txt`，**无需新增依赖**；
Alembic 已在用（`alembic/versions/` 下有一个 init 版本），新表走 autogenerate。

## 一、数据模型（5 张新表 + `users` 两列）

全部沿用 `app/db/base.py` 的 `big_pk()` / `big_fk()` / `TimestampMixin` / `utcnow()`，
索引命名范式参考 `app/models/favorite.py`。**新模型必须加进 `app/models/__init__.py` 的导入与 `__all__`**，否则 Alembic autogenerate 看不到。

### `follows`（关注）
| 列 | 说明 |
|---|---|
| `follower_id` | 关注者，`big_fk("users.id", ondelete="CASCADE")` |
| `followee_id` | 被关注者，同上 |
| `created_at` | |

`UniqueConstraint("follower_id","followee_id", name="uk_follow_pair")`；
`Index("ix_follow_follower","follower_id","created_at")`（我关注谁 / 关注流）；
`Index("ix_follow_followee","followee_id","created_at")`（粉丝列表 / fan-out）。

用 **CASCADE** 而不是 SET NULL：`admin/users.py::delete_user` 是物理删除用户，
关系行是纯从属数据，无审计价值；SET NULL 会让 `follower_id` 变 NULL，破坏唯一约束语义。
两个 FK 指向同一张表，**不加 `relationship()`**（避免 `foreign_keys=` 的复杂度），查询直接拼 `select`。

### `notifications`（站内通知）
| 列 | 说明 |
|---|---|
| `user_id` | 接收者，CASCADE |
| `actor_id` | 触发者，nullable + **SET NULL** |
| `image_id` | 相关图片，nullable + **SET NULL** |
| `type` | `String(24)`，常量 `NOTIF_IMAGE_PUBLISHED="image_published"`，预留 `follow`/`system` |
| `title` | `String(120)`，**文案快照** |
| `is_read` | Boolean default False |
| `created_at` | |

`Index("ix_notif_user","user_id","is_read","id")`：一条索引同时服务未读数 COUNT（索引覆盖）和列表分页。
`relationship("Image", lazy="selectin")` 用于列表取缩略图。
`title` 存快照的理由：通知是事件记录，图片后来被下架或改名不该改写历史文案（与 `audit_logs.reason` 同一思路）。
`actor_id` / `image_id` 用 SET NULL：通知要比它指向的对象活得久。

### `conversations`（会话，配对归一化）
| 列 | 说明 |
|---|---|
| `user_a_id` / `user_b_id` | CASCADE；**写入前强制 `sorted((me, other))`，a 恒为较小 id** |
| `last_message_at` | nullable |
| `last_message_preview` | `String(120)`，nullable |
| `last_sender_id` | nullable + SET NULL（前端据此显示「我: xxx」） |
| `created_at` / `updated_at` | TimestampMixin |

`UniqueConstraint("user_a_id","user_b_id", name="uk_conv_pair")`；
`Index("ix_conv_a","user_a_id","last_message_at")` + `Index("ix_conv_b","user_b_id","last_message_at")`。

归一化 + 唯一约束是「一对用户只有一条会话」的唯一可靠保证（靠 `IN` 查重在并发下会写重）。
冗余 `last_message_*` 让会话列表一次查询拿全，避免对每条会话再查最新消息（N+1）。
**刻意不加 `last_message_id` 外键**：会与 `messages` 形成循环 FK，MySQL 建表无法排序。

### `messages`（私信）
`conversation_id`（CASCADE）、`sender_id`（CASCADE）、`content String(2000)`、`is_read` Boolean、`created_at`。
`Index("ix_msg_conv","conversation_id","id")` + `Index("ix_msg_conv_read","conversation_id","is_read")`。
`is_read` 只对接收方有意义；标记已读 = `UPDATE ... WHERE conversation_id=? AND is_read=0 AND sender_id<>?`。
纯文本，不做 `kind` 字段（将来加图片消息再补）。

### `user_blocks`（屏蔽）
`blocker_id` / `blocked_id`（均 CASCADE）+ `created_at`。
`uk_block_pair` + `ix_block_blocker("blocker_id","created_at")` + **`ix_block_blocked("blocked_id")`**
（后者是必须的：发消息前要反向检查「对方是否屏蔽了我」，与主查询方向相反）。

### `users` 新增两列（头像）
```python
avatar_backend: Mapped[str | None] = mapped_column(String(8))    # local / s3
avatar_key:     Mapped[str | None] = mapped_column(String(255))
```
`avatar_url` **保留但降级为「外链兼容列」**。读取优先级：`avatar_key` 非空 → `url_for(avatar_backend, avatar_key)`；
否则回落 `avatar_url`（历史手填值仍然可用）。

为什么不把现算 URL 写回 `avatar_url`：写死就违反项目硬约束「库里只存 key，URL 现算」，
一旦把 `STORAGE_BACKEND` 从 local 切到 s3，所有老头像（存的是 `/media/...`）会立刻 404。

### 不给 `users` 加关注/粉丝冗余计数
实时 COUNT 走 `ix_follow_*` 索引覆盖，单机微秒级且天然正确；
冗余列在用户被物理删除时（CASCADE 不更新计数）会**永久漂移**，而关注关系没有像审核那样的自然重算节点。
未读数同理实时 COUNT。唯一例外是会话列表的预览 —— 那是会话自身属性，放 `conversations` 冗余列是对的。

## 三、后端接口清单

`auth` = `get_current_user`，`opt` = `get_optional_user`。分页统一 `page_params()`，错误用 `app.core.errors`。

### 1. 头像
| 方法 | 路径 | 请求 | 响应 | 鉴权 | 限流 |
|---|---|---|---|---|---|
| POST | `/api/me/avatar` | multipart `file` | `UserOut` | auth | `rate_limit("avatar",10,600)` |
| DELETE | `/api/me/avatar` | - | `MessageOut` | auth | - |

`POST` 流程（写在 `routers/me.py`，`def` 路由）：
1. `content_type` 白名单复用现有 `_ALLOWED_CONTENT_TYPES`（jpg/png/webp）；**独立上限 2MB**（不要用 `MAX_UPLOAD_MB=20`）。
2. Pillow 打开 → `ImageOps.fit(img,(512,512), Image.LANCZOS)` 居中裁方 → 存 WEBP（quality 88）。
3. key = `f"avatars/{user.id}/{uuid4().hex}.webp"` —— **必须带 uuid**：`routers/media.py` 给 `/media/**` 发了 `Cache-Control: immutable, max-age=31536000`，key 不变浏览器永远不刷新头像。
4. `storage.save(key, buf.getvalue(), "image/webp")` → 写 `avatar_backend/avatar_key` → **用旧 backend 实例** `get_storage(old_backend).delete(old_key)` 清理旧文件。
5. 提交并返回 `UserOut`。`DELETE` 则两列置空 + 删文件，回落到昵称首字母。

新增 `services/user_service.py::avatar_url_of(user)`。

**影响面收口（关键）**：不要逐个改调用点，在 `schemas/user.py::UserBrief` 上加一个 `mode="before"` 的
`@model_validator`：非 ORM 输入原样返回；是 ORM 对象则把整张表的列字典取出、用 `avatar_url_of()` 覆盖
`avatar_url` 字段后返回（**必须返回完整列字典**，否则 `UserOut`/`UserPublic` 等子类会因为缺字段校验失败）。
这样 `UserOut` / `UserPublic` / admin 用户列表 / 图片作者信息 / 登录注册响应**全部自动生效**，不漏点。

`PATCH /api/me` 的 `ProfileUpdateIn` 保留 `avatar_url`（允许外链、不破坏兼容），但前端不再暴露这个输入框。

### 2. 关注（统一用 username 定位，与既有 `GET /api/users/{username}` 和前端 `/u/:username` 一致）
| 方法 | 路径 | 响应 | 鉴权 |
|---|---|---|---|
| POST | `/api/users/{username}/follow` | `{is_following, follower_count}` | auth |
| DELETE | `/api/users/{username}/follow` | 同上 | auth |
| GET | `/api/users/{username}/followers?page&size` | `Page[UserBrief]` | opt |
| GET | `/api/users/{username}/following?page&size` | `Page[UserBrief]` | opt |
| GET | `/api/users/{username}` | **扩展**为 `UserPublic` + `following_count`/`follower_count`/`is_following` | opt（原来是免鉴权） |

规则（`services/follow_service.py`）：目标不存在或 `is_active=False` → `NotFoundError`（与现有实现一致，不泄漏账号状态）；
自关注 → 400；**被对方屏蔽 → 403「对方已屏蔽你」**；**我已屏蔽对方 → 400「请先解除屏蔽」**；
取关用 `rowcount` 判存在（同 `remove_favorite` 写法）。粉丝数与关注结果同一事务返回，省一次请求。
`GET /{username}` 改为手工装配 `user_service.to_public(db, target, viewer)`，因为 `is_following` 依赖 viewer。

### 3. 关注流（**扩展现有接口，不新开路由**）
`GET /api/images` 增加 `scope: str | None = Query(None, pattern="^(following|all)$")`：
```python
if scope == "following":
    if user is None:
        raise UnauthorizedError("请先登录后查看关注流")
    stmt = stmt.where(Image.owner_id.in_(
        select(Follow.followee_id).where(Follow.follower_id == user.id)))
```
基于 `image_service.public_query()`，自动继承 `PUBLIC_FILTER`（关注流只应看到已通过 + 未删除 + 处理完成的图）。
用 **`IN (子查询)` 而不是 `join(Follow)`**：join 会与已有的 Category/User join 叠加并放大计数，
子查询不放大行数且 MySQL 8 会做半连接优化。
未登录抛 401（前端拦截器据此跳登录），前端仍应在点击时先判 `auth.isLoggedIn`。
**前端 `ImageFeed.vue` 零改动**，只传 `:params="{ scope: 'following' }"`。

### 5. fan-out（两个触发点，一个公共函数）
**触发点 1**：`services/audit_service.py::approve()`（管理员在审核队列通过）。
**触发点 2**：`app/imaging/pipeline.py` 的 `becomes_public` 分支（L120-134，管理员上传 `source=official` 处理完自动通过，
跑在 `tasks/runner.py` 的**图片处理线程池**里，不是 HTTP 线程 —— 最容易漏的一处）。

`services/notification_service.py::fanout_image_published(db, image) -> list[int]`：
先 `SELECT follower_id`（推送名单），再用**一条 `INSERT ... SELECT`** 落库（不做逐条循环），返回接收者 id。
调用位置：`approve()` 里 `db.flush()` 之后、`db.commit()` 之前（与 `counter_service.refresh_for_image` 同事务，
避免「图已公开但通知没发」）；`pipeline.py` 里则在 `refresh_for_image` 之后、commit 前调用，commit 后再推送。

**必须用 `from_status != AUDIT_APPROVED` 守卫**：`approve()` 允许对「已下架」的图再次 approve（恢复上架路径），
不守卫就会给关注者重复轰炸；`restore()` 走另一条路径，天然不触发。

### 6. 私信
| 方法 | 路径 | 响应 | 鉴权 | 限流 |
|---|---|---|---|---|
| GET | `/api/messages/conversations?page&size` | `Page[ConversationOut]` | auth | - |
| GET | `/api/messages/{username}?before_id&after_id&limit=30` | `CursorPage[MessageOut]` | auth | - |
| POST | `/api/messages/{username}` | `MessageOut` | auth | `rate_limit("message",60,60)` |
| POST | `/api/messages/{username}/read` | `{unread_count}` | auth | - |

`ConversationOut` = `{id, peer: UserBrief, last_message_preview, last_message_at, last_sender_id, unread_count}`。

- 会话列表：`UNION ALL` 两半查询（`user_a_id=me` / `user_b_id=me`）取分页后的 id，再按 id 取会话行 + 对端 User，
  在 Python 里按 id 顺序重排；未读数用**一次 `GROUP BY` 聚合**（不是逐个会话查）。
- 消息分页**用游标（`before_id`）不用 offset**：聊天中不断有新消息插入，offset 在向上翻历史时会漂移。
  `WHERE conversation_id=? AND (before_id IS NULL OR id < before_id) ORDER BY id DESC LIMIT limit+1`，
  取 `limit+1` 判 `has_more`；`items` 按 `id ASC` 返回供前端 concat 到顶部。
  需要 `CursorPage`（新增到 `schemas/common.py`）：`{items, has_more, next_before_id}`。
  `after_id` 供 WS 降级时的增量补齐（与 `before_id` 互斥）。
- 发消息（`services/message_service.py::send`）：自己给自己 → 400；**双向屏蔽检查** → 403 `code="BLOCKED"`；
  `content.strip()` 为空 → 400；`sorted()` 求 (a,b) → 查会话，不存在则 INSERT（并发靠 `uk_conv_pair` + `IntegrityError` 兜底，
  写法同 `add_favorite`）；插入消息 → `UPDATE conversations` 三个冗余列；commit 后推送对端 + 自己（多标签页同步）。
  `preview` 截断 120 字（`[:117]+"..."`）。

### 7. 屏蔽
| 方法 | 路径 | 响应 | 鉴权 |
|---|---|---|---|
| POST | `/api/users/{username}/block` | `{is_blocked: true}` | auth |
| DELETE | `/api/users/{username}/block` | `{is_blocked: false}` | auth |
| GET | `/api/me/blocks?page&size` | `Page[UserBrief]` | auth |

语义 **取双向阻断**：
- 发送侧双向检查（不存在 A→B 屏蔽 且 不存在 B→A 屏蔽 才允许发送）。只做「我不接收」会造成
  「B 显示已发送、A 永远收不到」的最差体验。
- 屏蔽时**顺手删除双向关注关系**（否则出现「已关注 + 已屏蔽」的矛盾态，也顺带缩小 fan-out 面）。
- 被屏蔽者**不能新关注我**，但**仍可浏览我的公开作品与主页**（屏蔽只作用于互动，不改 `public_query()`）。

## 四、WebSocket 实时推送（重点）

原则：**WS 只做实时性增强，所有消息/通知先落库，推送失败不影响业务成功** —— 这是降级方案成立的前提。

### 连接管理器 `backend/app/realtime/manager.py`
`dict[int, set[WebSocket]]`（一个用户 N 个标签页全保留）+ `threading.Lock` 保护跨线程访问 + `_loop` 保存事件循环。
`register` / `unregister`（集合空了必须 `del`，否则长期运行累积空键）/ `snapshot(user_ids)`。

```python
def push_to_users(user_ids, payload) -> None:
    """同步函数，任意 HTTP 线程 / 图片处理线程池都可调用。永不抛异常。"""
    loop = manager._loop
    if loop is None or loop.is_closed():
        return                                   # 启动早期或关停中：静默降级
    targets = manager.snapshot(user_ids)
    if not targets:
        return
    try:
        fut = asyncio.run_coroutine_threadsafe(manager._send_many(targets, payload), loop)
    except RuntimeError:
        return                                   # loop 已关闭
    fut.add_done_callback(...)                   # 只记日志，绝不 .result() 阻塞业务线程
```

### 拿事件循环：只在 `main.py` 的 `lifespan` 里抓
```python
manager.bind_loop(asyncio.get_running_loop())   # 唯一可靠的时机
```
不要用 `asyncio.get_event_loop()`（3.10+ 在非循环线程会警告/报错），不要在模块顶层抓。
所有 `await ws.send_*` 只出现在 `_send_many` 里、只在 loop 线程执行 —— 从根上避免
`RuntimeError: ... is bound to a different event loop`。

### 握手鉴权 `routers/ws.py`
浏览器 WebSocket 不能带自定义 header，所以 **token 走 query**：
`/api/ws?token=...`，用 `SessionLocal()` 复用 `deps._resolve_user` 的语义（含 `is_active` 检查，补偿 7 天 token 无吊销机制）；
无效则 `await websocket.close(code=4401)`（不能抛 `UnauthorizedError`，WS 不走 HTTP 异常处理器）。
`WS` 路由必须在 `mount_frontend(app)` **之前**注册。

### 生命周期与心跳
`accept()` → `register` → 先推 `{"type":"hello","unread":{...}}` → 循环接收，只认 `{"type":"ping"}` 回 `pong`；
`WebSocketDisconnect` → `unregister`。
- 多标签页：集合全部保留，发送失败的连接立刻 unregister（不给死连接反复重试）。
- 传输层：uvicorn 的 websockets 默认 `ping_interval=20s` 自动探测半开连接，无需配置。
- 应用层：前端每 25s 发 ping，60s 未收到 pong 主动 close 并重连（浏览器 WS 半开时不会触发 onclose）。
- **不做离线消息队列**：离线消息本来就在库里，重连后走 REST 补齐。

### 前端 `stores/realtime.js`（Pinia）
state：`status('idle'|'connecting'|'open'|'closed'|'polling')`、`unread`、内部 `_ws/_retry/_timer/_hb`、`_listeners`。
**所有写操作走 REST，WS 只推不收**。
- URL：`ws(s)://${location.host}/api/ws?token=...`（生产同源 8000；开发走 Vite proxy，需 `vite.config.js` 的 `/api` proxy 加 `ws: true`）。
- 重连：指数退避 `min(30000, 1000*2**retry)` + ±20% 抖动；`online` 事件与 `visibilitychange` 切回前台时立即重置退避重连；
  连续失败 5 次降级为纯轮询（`status='polling'`，每 30s 调 `refreshUnread()`）。
- onmessage 分发：`hello` 写 unread；`notification` → 未读 +1；`message` → **若 `sender_id === auth.userId` 不加未读**（多标签页同步），
  否则不在该会话页则未读 +1；`pong` 记时间。然后广播给 `_listeners`。
- 启停：`App.vue` 的 `onMounted` 里 `watch(() => auth.isLoggedIn, v => v ? rt.connect() : rt.disconnect(), { immediate: true })`。

### 降级矩阵
| 场景 | 行为 |
|---|---|
| 未登录 / 已登出 | 不建连，不显示红点 |
| 建连被拒 4401 | 先 `refreshUnread()`，无 token 则停 |
| 浏览器不支持 / 被代理阻断 | `status='polling'`，导航栏未读 30s 轮询 |
| 消息中心打开但 `status!=='open'` | 当前会话 5s 增量轮询 `GET /api/messages/{u}?after_id=` |
| 重连成功 | 立即 `refreshUnread()` + 当前会话拉增量补齐 |

### 既有配置的影响（已核实）
`MEDIA_URL_PREFIX`、`CORSMiddleware`（只管 HTTP 响应头）、`mount_frontend` 的 catch-all（只匹配 HTTP GET）**都不影响 WS**；
`rate_limit` 是 HTTP 依赖，不作用于 WS（刷屏由 REST 的 `rate_limit("message",60,60)` 挡）；
**必须保持单进程运行**（连接表在进程内存里，`--workers > 1` 推送必丢，与 `core/ratelimit.py` 的假设一致）。

## 六、风险与取舍

1. **fan-out 规模**：单条 `INSERT ... SELECT` + 单事务，粉丝 ≤5000 时同步执行可接受（审核是低频动作）。再大就分批或另起线程池（**不要复用 `tasks/runner.py`**，那是图片处理专用池）。
2. **fan-out 重复触发**：靠 `from_status != AUDIT_APPROVED` 守卫（恢复上架路径）。
3. **消息表增长**：`(conversation_id, id)` 覆盖分页；会话列表靠冗余列免扫表；未读只对当前页会话做 `GROUP BY`。单会话上万条后把 `is_read` 换成「会话内已读游标」（`conversations` 加两列），接口语义不变。
4. **WS 单进程限制**：`--workers > 1` 推送必丢。多进程需 Redis pub/sub，届时只换 `push_to_users` 的实现，调用方零改动。
5. **WS token 走 query**：会进日志/浏览器历史。本地部署可接受；要更强可改用 `Sec-WebSocket-Protocol` 子协议。**不要**改成 cookie（与 Bearer 体系冲突，且 `allow_credentials=False`）。
6. **屏蔽语义**：双向阻断；被屏蔽者仍可浏览公开作品（不改 `public_query()`）。
7. **头像 key 必须带 uuid**（`/media` 是 immutable 缓存），换头像要换 key 才能刷新。
8. **私有消息无内容审核**：靠长度上限 2000 + 频率限制 60 条/分 + 屏蔽机制约束。
9. **未读数是推导值**：WS 只做增量提示，页面每次进入 / 切 tab / 重连都调 `refreshUnread()` 做真值校正，避免长时间挂机后红点失真。
10. **`scope=following` 的 401 跳转**：前端应先在点击时拦截，避免「点了才跳」的突兀感。
